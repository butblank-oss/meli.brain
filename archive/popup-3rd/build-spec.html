0. 너가 만들 것

인천 남동구 치매안심센터에서 2026년 10월 30일(금) 하루 진행하는 오프라인 팝업 행사에서, 원메딕스 임직원이 노트북으로 어르신을 응대하며 설문을 입력하는 웹 앱이다. 어르신이 쓰는 앱이 아니라 직원이 쓰는 입력 도구다.

  • 대상자 명단 1,523명 (인천 남동구 치매안심센터 소속 중 유효 계정)
  • 동시 사용 직원 3~6명, 각자 노트북
  • 행사 당일 하루, 1인당 응대 3~12분
  • 현재 프로토타입이 단일 HTML 파일로 존재하나, 아래 결함 때문에 새로 만든다

기존 프로토타입에서 반드시 고쳐야 할 결함

  1. 완료 판정이 암묵적이라 미완성 레코드가 대량 발생한다. 명시적 완료 버튼이 없었다.
  2. 필수값 표시만 있고 검증이 없었다.
  3. 온라인 필수라 와이파이가 끊기면 응대가 멈춘다.
  4. 한 화면에 문항 10~14개가 세로로 쌓여 응대자가 스크롤로 문항을 찾았다.
  5. 입력 중 다른 기기의 동기화가 들어오면 저장 안 된 입력값을 덮어썼다.
  6. 개인정보 열람 기록이 전혀 없었다.
  7. 행사 중에도 관리자가 설문 구조를 바꿀 수 있어 데이터가 깨질 위험이 있었다.

1. 절대 제약

1-1. 코드와 저장소에 개인정보를 넣지 마라. GitHub Pages는 정적 호스팅이며, 저장소가 private이어도 Pages로 배포된 파일은 공개된다. 참여자 명단은 반드시 DB에만 존재해야 한다. roster.json 같은 명단 파일을 저장소에 커밋하는 구현은 금지한다. 원본 CSV는 .gitignore에 넣어라.

1-2. 로그인 없이는 아무 데이터도 보이지 않아야 한다. Supabase Auth로 인증하고, 모든 테이블에 RLS를 걸어 authenticated 역할만 접근 가능하게 한다. 익명 키는 번들에 노출되지만 RLS가 막는다.

1-3. 오프라인에서도 응대가 끊기지 않아야 한다. 로컬(IndexedDB)에 먼저 쓰고 온라인일 때 동기화하는 구조다. 네트워크 상태는 화면에 항상 표시한다.

1-4. 저장 안 된 입력을 덮어쓰지 마라. 서버에서 온 데이터가 로컬의 미동기화 변경을 덮어쓰면 안 된다. 필드 단위로 updated_at을 비교하거나, 동기화 대기 중인 레코드는 서버 데이터를 무시한다.

2. 기술 스택

  • Vite + React + TypeScript
  • Tailwind CSS
  • Supabase (Postgres + Auth + Realtime)
  • IndexedDB는 Dexie 사용
  • 배포: GitHub Actions로 빌드해서 GitHub Pages
  • Supabase URL과 anon key는 GitHub Actions의 Repository Variables로 주입 (VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY)
  • 테스트: Vitest + React Testing Library, 6절의 수용 기준을 테스트로 작성

Vite base 설정을 저장소 이름에 맞춰라. SPA 라우팅은 GitHub Pages에서 404가 나므로 HashRouter를 쓰거나 404.html 리다이렉트를 넣어라.

3. 데이터 모델

3-1. participants (명단, 읽기 전용)

컬럼 타입 설명
id uuid PK 계정 ID
name_masked text 마스킹 이름 (김*자)
phone_last4 text 휴대폰 뒷 4자리
birth_year text 생년 4자리, 없을 수 있음
age_group text 60 70 80 90 ?
sex text F M ?
days_since_last_activity int 미사용자는 null
total_activity_cnt int 누적 활동 횟수
cohort text 26 2 ?
track text A B C (임포트 시 계산)
snapshot_date date 데이터 추출 기준일

실명, 생년월일 전체, 이메일, 전체 전화번호는 저장하지 마라. 실명은 응답 테이블에 직원이 입력한 값만 들어간다.

3-2. responses (응답)

컬럼 타입 설명
id uuid PK
participant_id uuid 명단 외 추가면 null
manual_info jsonb 명단 외일 때 이름·뒷4자리·연령대·성별·사유
track text 확정된 트랙
verified text ok failed skipped
verified_by / verified_at text / timestamptz
real_name text 리워드 배송 확인용, 선택 입력
consent text 동의 미동의
helpers text[] 도와준 담당자 (복수)
answers jsonb 질문 key → 값 (문자열 또는 문자열 배열)
status text in_progress done refused revisit
result text 응대 결과
entered_by text 입력자
started_at / completed_at timestamptz
updated_at timestamptz
client_rev int 충돌 해소용 증가 카운터

participant_id에 부분 유니크 인덱스를 걸어 중복 응답을 막아라 (명단 외는 예외).

3-3. survey_schema (설문 정의)

id, version int, payload jsonb, locked bool, updated_by, updated_at.

locked=true면 어떤 계정도 수정 불가. 행사 당일 아침에 잠근다.

3-4. staff (담당자 명단)

id, name, active bool, role (admin | operator), auth_user_id.

초기값: 강하연, 김다희, 김도영, 김성정, 김소리, 김철순, 노준성, 박유라, 안성호, 윤종훈, 이승민, 이용혁, 홍지혜

3-5. access_log (열람 기록)

id, participant_id, staff_name, action (view | verify | export | delete), at.

보건소 케어센터 어드민은 개인정보 원문 열람 시 사유 입력과 2년 보관을 요구한다. 현장 속도 때문에 사유 입력은 받지 않되, 모든 열람을 자동 기록한다. 기록 보관 기간과 사유 입력 필요 여부는 보건소 협의 사항이므로 reason 컬럼을 nullable로 미리 만들어 두어라.

3-6. RLS

  • 모든 테이블: authenticated만 select
  • participants: 클라이언트에서 insert/update/delete 불가. 임포트는 service role 스크립트로만.
  • responses: authenticated가 insert/update 가능, delete는 소프트 삭제(deleted_at)로 처리하고 하드 삭제는 막아라.
  • survey_schema: update는 staff.role='admin'인 사용자만. locked=true면 전부 거부.
  • access_log: insert만 허용, update/delete 불가.

4. 화면 명세

전체 흐름은 한 번에 한 단계다. 이전 프로토타입처럼 모든 문항을 한 화면에 쌓지 마라.

4-0. 로그인

Supabase Auth 매직링크 또는 이메일+비밀번호. 로그인 후 staff 테이블에서 본인 이름을 고른다(최초 1회, 로컬 저장).

4-1. 상단 바 (항상 노출)

  • 입력자 이름 (드롭다운, staff 명단)
  • 네트워크 상태: 동기화됨 / 대기 N건 / 오프라인. 대기 건수는 반드시 숫자로 보여라.
  • 진행 현황: 트랙별 완료 / 전체, 현장 첫 게임 실행 건수
  • 버튼: 게임 카드 인쇄, 응답 내보내기, 설문지 편집(admin만)

4-2. 찾기

  • 검색창 하나. 입력값이 숫자면 전화 뒷 4자리로, 문자면 이름으로 검색한다.
  • 이름 검색은 마스킹을 감안해야 한다. 간경자를 입력하면 간*자가 나와야 한다. 규칙: (a) 입력값이 이름에 그대로 포함, (b) 길이가 같고 * 자리를 무시한 문자가 전부 일치, (c) *를 뺀 글자들이 입력값 안에 순서대로 등장, (d) 첫 글자 일치. 넷 중 하나라도 맞으면 후보로 띄운다.
  • 결과 행에 뒷 4자리를 반드시 표시한다. 마스킹 이름만으로는 절반 이상이 동명이인이다.
  • 필터: 트랙 A/B/C, 상태(미착수·진행중·완료), 기수(26년·2기)
  • 검색창에 ✕ 버튼
  • 결과 0건일 때: "전화 뒷 4자리로 찾아보세요. 이쪽이 훨씬 정확합니다" 안내 + 명단에 없는 분 추가 버튼

4-3. 본인 확인 (설문 전 필수 관문)

선택한 어르신의 카드를 띄운다. 화면 중앙에 큰 글씨로:

"전화번호 뒷 네 자리가 어떻게 되세요?"

아래에 뒷 4자리(가장 크게), 생년, 연령·성별, 마스킹 이름, 기수, 트랙을 표시한다. 전체 성함 입력칸(선택)을 둔다.

버튼 세 개:

  • 본인 확인 완료 → 다음 단계
  • 다른 분입니다 → 검색으로 복귀
  • 확인 못 했지만 진행 → verified='skipped'로 기록하고 진행

이 단계를 통과하지 않으면 설문 문항이 보이지 않아야 한다. 통과 시 access_log에 verify 기록.

중복 응대 방지: 다른 직원이 이미 이 어르신을 진행 중이면 경고를 띄우고, 이어받을지 취소할지 묻는다. Realtime 구독으로 감지한다.

4-4. 단계형 설문

스텝 인디케이터(2 / 5)를 상단에 고정한다. 한 스텝에 질문 3~4개까지만 둔다.

  • 스텝 1: 개인정보 동의, 도와준 담당자
  • 스텝 2~4: 트랙별 문항 (A는 2스텝, B는 3스텝, C는 3스텝 권장)
  • 마지막 스텝: 리워드 처리, 4기 사전신청, 응대 결과, 메모

규칙:

  • 이전 / 다음 버튼. 필수값이 비면 다음을 막고 해당 문항을 붉게 표시한다.
  • 트랙 C는 조치 스텝에 체크리스트를 둔다. 설치, 로그인, 첫 게임 실행을 체크하고 막힌 지점을 기록한다.
  • 마지막 스텝의 버튼은 응대 완료다. 누르면 status='done', completed_at 기록, 완료 화면으로 넘어간다. 완료 화면에 "다음 분 찾기" 버튼을 크게 둔다.
  • 중간에 목록으로 나가면 status='in_progress'로 남고, 목록에 진행중 배지와 입력자 이름이 뜬다.

4-5. 명단 외 추가

성함, 전화 뒷 4자리, 연령대, 성별, 명단에 없는 이유(재등록 / 등록 지연 / 이전 기수 / 가족 대리 / 모름), 트랙을 받고 같은 설문 흐름으로 진입한다.

4-6. 어드민 (role=admin)

  • 설문 문항 편집: 섹션(접수·A·B·C·마무리)별 목록, 순서 변경, 추가·복제·삭제, 유형(하나 선택·여러 선택·담당자 선택·짧은 글·긴 글·구분선), 문구, 도움말, 필수 여부, 표시 조건, 보기 목록
  • 담당자 명단 편집
  • 트랙별 안내문 편집
  • 행사 잠금 토글: 잠그면 survey_schema.locked=true가 되어 아무도 수정할 수 없다. 잠금 해제는 확인 절차를 두 번 거치게 하라.
  • 저장 시 version을 올리고, 접속 중인 모든 클라이언트에 Realtime으로 전파한다.
  • 이미 응답이 존재하는 질문의 key를 바꾸려 하면 경고하고 막아라.

4-7. 게임 카드 인쇄

게임 목록을 큰 글씨 카드로 인쇄하는 화면. A4 가로, 한 장에 2~4장. 트랙 B에서 어르신에게 짚게 하는 용도다. 목록은 어드민에서 편집한 보기와 동기화된다.

기본 게임 17종: 기억의 숨바꼭질, 오늘의 장바구니, 숨은 헬씨 찾기, 꿀벌의 숫자놀이, 초성 퀴즈, 재밌는 숫자 퍼즐 4X4, 구슬 옮기기, 기찻길 만들기, 숨은 헬씨찾기 비밀작전, 양말정리 대작전, 진짜 색깔 찾기, 단어 기억하기, 알쏭달쏭 숫자 더하기, 재밌는 숫자 퍼즐 9X9, 색깔 맞추기, 이상한 신호, 타일 뒤집기

운영 중인 게임이 13종이라는 자료가 있으므로, 임포트 후 실제 목록을 확인해 조정할 수 있게 어드민에서 편집 가능해야 한다.

5. 임포트 스크립트

scripts/import-participants.ts를 만들어라. service role 키로 실행하는 Node 스크립트이며 저장소에 키를 커밋하지 않는다.

입력은 운영 DB 추출본 S3_user_info.csv다. 실제 컬럼명은 다음과 같다.

user_id, name_masked, nickname, birthdate, birthyear, mobile_masked,
email_masked, sex, user_type, status, created_date, last_login_date,
age_group, sex_label, provider_names, challenge_names, challenge_cnt,
total_activity_cnt, completed_activity_cnt, last_activity_date_kst,
days_since_last_activity, last_activity_material_type,
registration_path, user_group, recent_signup_flag, user_status

처리 규칙:

  1. provider_names에 인천 남동구 치매안심센터가 포함된 행만 가져온다 (약 1,561행).

  2. 아래에 해당하는 행은 명단에서 제외한다. 현장에 나타나면 명단 외 추가로 처리한다.

    • name_masked가 비어 있는 행 (8건). 이름이 없으면 현장에서 본인 확인 자체가 불가능하다.
    • name_masked에 PRD TEST 테스트 개발 샘플이 들어간 행 (3건)
    • user_status='withdrawn'인 행 (27건). 탈퇴 계정은 응대 대상이 아니다.

    총 38건이 빠져 1,523명이 남는다.

  3. mobile_masked는 +8210****8800 형식이다. 숫자만 남겨 마지막 4자리를 phone_last4로 쓴다.

  4. birthyear를 birth_year로 쓴다. 비어 있으면 null (약 167건).

  5. age_group에서 대를 떼고, 미상과 0대는 ?로 바꾼다.

  6. sex_label이 female이면 F, male이면 M, 나머지는 ?.

  7. challenge_names에 26년이 있으면 cohort='26', 2기가 있으면 '2', 아니면 '?'.

  8. 트랙 판정: days_since_last_activity(이하 dsl), total_activity_cnt(이하 tot)

    • dsl이 비어 있으면 C
    • dsl ≤ 30 이면 A
    • dsl > 30 이고 tot > 20 이면 B
    • 그 외 C

  9. nickname, birthdate, email_masked, mobile_masked 전체는 저장하지 마라.

  10. user_id 기준 upsert. 재실행해도 응답 데이터가 깨지지 않아야 한다.

2026-09-14 기준 추출본으로 돌리면 총 1,523명에 A 351명, B 454명, C 718명이 나온다 (기수별로는 26년 891명, 2기 582명, 미상 50명). 이 숫자가 크게 다르면 임포트 로직을 의심하라.

행사 전 2026년 10월 25일경 데이터를 재추출할 예정이다. 재임포트 시 트랙이 바뀌는 인원이 생기므로, 또 그 사이에 탈퇴한 사람이 명단에서 빠지므로, 이미 status='done'인 응답의 track은 덮어쓰지 말고 participants.track만 갱신하라.

데이터 보호

  1. 빌드 산출물(dist/) 어디에도 참여자 이름·전화번호·명단이 포함되지 않는다.
  2. 로그아웃 상태에서 API를 직접 호출하면 모든 테이블이 빈 결과 또는 403을 반환한다.
  3. participants에 대한 클라이언트 insert/update/delete가 실패한다.

식별 4. 간경자로 검색하면 간*자가 결과에 나온다. 5. 8800으로 검색하면 뒷 4자리가 8800인 사람만 나온다. 6. 검색 결과 행에 뒷 4자리가 표시된다. 7. 본인 확인을 통과하지 않으면 설문 문항이 렌더링되지 않는다.

입력 안정성 8. 실명 입력칸에 타이핑한 뒤 다른 문항의 보기를 클릭해도 입력값이 유지된다. 9. 보기를 클릭해도 화면 스크롤 위치가 유지된다. 10. 입력 중 서버에서 같은 레코드의 이전 버전이 도착해도 로컬 입력값이 덮어써지지 않는다.

완료 판정 11. 필수 문항이 비어 있으면 다음이 막히고 해당 문항이 강조된다. 12. 응대 완료를 누르기 전에는 status가 done이 되지 않는다. 13. 완료 후 진행 현황 숫자가 즉시 증가한다.

오프라인 14. 네트워크를 끊은 상태에서 설문을 끝까지 입력하고 완료할 수 있다. 15. 오프라인 중 상단에 오프라인 · 대기 N건이 표시된다. 16. 네트워크 복구 후 자동으로 동기화되고 대기 건수가 0이 된다. 17. 탭을 새로고침해도 오프라인 입력 내용이 남아 있다.

동시 작업 18. 두 브라우저에서 같은 어르신을 열면 나중에 연 쪽에 경고가 뜬다. 19. 한쪽에서 완료하면 다른 쪽 목록에 즉시 반영된다.

어드민 20. operator 역할로는 설문지 편집 화면에 진입할 수 없다. 21. locked=true일 때 admin도 저장이 거부된다. 22. 응답이 존재하는 질문의 key 변경 시도가 차단된다.

내보내기 23. CSV에 트랙·본인확인 상태·확인자·입력자·응답 전체가 포함된다. 24. 여러 선택 항목이 구분자로 합쳐져 한 칸에 들어간다. 25. Excel에서 한글이 깨지지 않는다 (BOM 포함).

7. 비기능 요구

  • 노트북 1440×900 기준. 본문 16px 이상, 버튼 높이 44px 이상.
  • 전체 흐름을 키보드만으로 완료할 수 있어야 한다. 검색창에서 Enter로 첫 결과 선택, 스텝 이동 단축키.
  • 1,523명 목록 렌더링이 버벅이지 않게 가상 스크롤 또는 결과 제한을 적용한다.
  • 5분마다 로컬에 전체 스냅샷을 백업하고, 상단에서 언제든 수동 내보내기가 가능하다.
  • 다크모드 대응은 하지 않아도 된다. 대신 밝은 조명 아래 대비를 충분히 확보하라.

8. 작업 순서

  1. Vite + React + TS + Tailwind 초기화, GitHub Actions로 Pages 배포 파이프라인 구성. 빈 화면이라도 먼저 배포까지 성공시켜라.
  2. Supabase 프로젝트 스키마와 RLS 마이그레이션 작성.
  3. 임포트 스크립트 작성 후 실제 CSV로 실행, 건수 검증.
  4. 로그인과 상단 바.
  5. 찾기 화면 + 검색 매칭 규칙 (수용 기준 4~6을 먼저 테스트로 작성).
  6. 본인 확인 관문.
  7. 단계형 설문 + 검증 + 완료 처리.
  8. 오프라인 큐와 동기화.
  9. 어드민과 잠금.
  10. 내보내기, 게임 카드 인쇄.
  11. 수용 기준 전체 통과 확인.
