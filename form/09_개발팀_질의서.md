## B. 현재 구조 확인 — 개발 착수 전에 알아야 하는 것 (9건)

기획이 "신청폼이 회원까지 만든다"를 전제로 잡혀 있어서, 지금 코드가 어떻게 돼 있는지에 따라 작업량이 크게 달라집니다.

| # | 질문 | 왜 |
|---|---|---|
| B-1 | **현재 신청폼**(`meli.health/invitations/dementia3/form`)의 스택과 저장소는? 제출 데이터는 어느 테이블에 쌓이고 어드민 어디서 봅니까? | 신규 개발인지 기존 확장인지가 갈립니다 |
| B-2 | **회원 테이블과 신청 테이블의 관계**는? 지금은 완전히 분리돼 있습니까? | "신청폼 제출 = 회원 생성"으로 합치려면 이 구조를 알아야 합니다 |
| B-3 | **전화번호만으로 앱 로그인**이 이미 되는 구조입니까? | 9/18 회의에서 "신청폼 작성자는 앱 설치 후 전화번호로 로그인만 하면 된다"고 했는데, 구현이 이미 있는지 확인이 필요합니다. 없으면 이게 가장 큰 작업입니다 |
| B-4 | **SMS 인증번호 발송·검증 로직**이 이미 있습니까? (NHN Cloud 연동) | 직원 대리 접수와 기존 회원 확인에 필요합니다. 없으면 신규 |
| B-5 | **승인 상태**는 어떤 필드/값입니까? (`대기` / `승인` enum?) 자동 승인은 이 값을 바로 세팅하면 되는 구조입니까? | 자동 승인 구현 방식 |
| B-6 | **보건소 소속 편입**은 어떤 값으로 표현됩니까? (`org_id` 같은 것) 신청폼 경로로 들어온 회원에게 자동으로 붙일 수 있습니까? | 관리자가 수동으로 넣던 거주동·소속을 자동화해야 합니다 |
| B-7 | **기수(3기 / 4기)가 데이터 모델에 있습니까?** 같은 회원이 여러 기수에 참여하는 구조가 이미 있습니까? | 3기 참여자가 4기를 신청할 때 기존 계정에 붙이는 처리(`FE-07`, `FS-08`)에 필요합니다 |
| B-8 | **거주 행정동 코드 체계**는? 행정동 코드입니까 법정동 코드입니까, 아니면 문자열입니까? | 관내 20개 화이트리스트 재검증(`FS-05`)을 서버에서 해야 합니다 |
| B-9 | **전화번호로 기존 회원을 조회하는 API**가 이미 있습니까? | 신청폼의 첫 단계가 이 조회입니다 |

## C. 서버가 구현해야 하는 것 — 요구사항 전달 (12건)

화면에서 막을 수 없고 **서버에서만 막을 수 있는** 것들입니다. 우선순위 순입니다.

| # | 요구 | 안 지키면 |
|---|---|---|
| **C-1** | **전화번호 조회 API 응답에 이름·거주 동을 포함하지 않는다.** 인증 통과 뒤 별도 호출로 내려준다 | 화면을 잠가도 네트워크 응답에 들어 있으면 그대로 보입니다. **가장 중요합니다** |
| **C-2** | **조회 API에 레이트 리밋** (IP·번호 단위) | 번호를 대입해 남동구 참여자 명단을 통째로 캐낼 수 있습니다 |
| **C-3** | **인증번호 검증·시도 횟수·잠금·재발송 쿨다운을 전부 서버에서 센다** | 클라이언트 조작으로 인증을 건너뜁니다. 화면의 `(3/5번째)`는 안내용일 뿐입니다 |
| **C-4** | **제출 시 거주 동 코드를 관내 화이트리스트로 재검증** | 클라이언트를 우회해 관외 신청이 자동 승인됩니다 |
| **C-5** | **제출 멱등 처리** — 같은 번호는 신규 생성 대신 기존 건 반환 | 연타·재시도로 중복 접수가 쌓입니다 |
| **C-6** | **미로그인 30일 계정 자동 정리** | 타인 번호로 만든 계정이 그 번호의 실제 소유자 가입을 영구히 막습니다. 신규 가입을 무인증으로 두기로 한 결정의 전제 조건입니다 |
| **C-7** | 동의 저장 시 **항목별 동의 여부 · 동의 시각 · 약관 버전 · 작성 경로**를 함께 기록 | 분쟁 시 동의를 입증할 수 없습니다 |
| **C-8** | 직원 대리 접수는 **`channel=staff_proxy`** 로 구분 저장 | 대리 작성 건을 사후에 가려낼 수 없습니다 |
| **C-9** | **인증 토큰에 짧은 유효기간**을 두고 제출 시 재검증 | 인증만 받아두고 나중에 다른 값으로 제출할 수 있습니다 (`FS-06`) |
| **C-10** | **완료 문자 발송을 제출 성공과 분리** (문자가 실패해도 접수는 유효) | 문자 장애가 가입 전체를 막습니다 (`FR-03`) |
| **C-11** | **미로그인 계정 정리의 실제 집행 시작일을 `2026-10-18` 이후로 설정** | 약관 제9조 2항 5호는 이번 개정으로 **새로 생긴 해지 사유**입니다. 시행일(2026-09-18)에는 30일 공지 기간이 확보되지 않아, 집행 시점을 30일 뒤로 미뤄 리스크를 줄이기로 했습니다. **C-6의 기능은 지금 만들되, 첫 삭제 배치는 10/18 이후에 돌려주세요** |
| **C-12** | **약관 개정 공지 게시 + 기존 회원 개별 통지(푸시 또는 문자)** 및 **발송 로그 보관** | 제3조 3항이 불리한 변경에 요구하는 절차입니다. 나중에 필요한 것은 날짜가 아니라 증거입니다 |

## D. 클라이언트 구현 시 주의 (5건)

프로토타입에서 실제로 물렸던 것들입니다.

| # | 내용 |
|---|---|
| D-1 | **조상 요소에 `overflow:hidden` 을 쓰지 마세요.** 제출 버튼의 `position:sticky` 가 조용히 죽습니다. 시각적으로 티가 안 나서 놓치기 쉽습니다 |
| D-2 | **고정 제출 바의 높이를 측정해서** "아래에 더 있어요" 배지 위치를 잡으세요. 고정값(124px)을 쓰면 글자 확대 시 바가 181px까지 자라 배지가 뒤로 숨습니다 |
| D-3 | **동의 행 전체 탭 + 체크박스 탭이 겹치면 토글이 상쇄됩니다.** 체크박스 버튼에서 이벤트 전파를 끊으세요 |
| D-4 | **임시저장·복구(`FX-05`)를 넣어주세요.** 어르신은 입력 중 전화를 자주 받습니다. 단 **직원 모드(공용 기기)에서는 저장하지 않고 기존 저장분도 지웁니다** |
| D-5 | **제출 버튼을 `disabled` 로 막지 마세요.** 항상 활성으로 두고, 누르면 빠진 항목까지 스크롤·포커스하고 이유를 띄웁니다. 비활성 버튼은 스크린리더가 읽지 않습니다 |
