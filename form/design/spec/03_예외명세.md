## AD — 관리자 승인 화면 (16)

보건소 담당자가 쓰는 모바일 웹(`admin.html`)의 예외입니다.
**한 손으로, 서서, 어르신을 기다리게 하면서** 쓰는 화면이라는 것이 모든 판단의 전제입니다.

**승인 화면 규칙 (AD-R)**

1. 확인할 신청이 기본 화면이다. 통계나 대시보드를 먼저 보여주지 않는다
2. 반려에는 **사유가 반드시 붙는다**
3. 처리 전에 **신청자에게 보일 문장**을 보여준다. 분류만 고르고 끝내지 않는다
4. 모든 처리는 되돌릴 수 있다
5. 상세 화면으로 들어가지 않는다. 판단에 필요한 정보를 목록 카드에 다 올린다
6. 의심 건은 붉은 줄로 먼저 알린다. 다만 **자동으로 반려하지는 않는다**
7. 처리자 · 시각 · 사유를 남긴다
8. 문자 발송 실패가 상태 전이를 막지 않는다

|---|---|---|

### 제출 이후 — 신청 건의 상태

여기서부터는 폼이 아니라 **신청 건**의 상태입니다. 관리자 승인이 생기면서 `SUBMITTING` 다음이 곧장 "이용 가능"이 아니게 됐습니다.

| 상태 | 진입 | 어르신이 보는 화면 | 앱에서 가능한 것 | 나가는 곳 |
|---|---|---|---|---|
| PENDING | 제출 성공 | SC-F-02 → 앱에서는 SC-A-02 | 설치 · 로그인 · 게임 · 걷기 (**교실은 잠김**) | 승인 → APPROVED / 반려 → REJECTED |
| APPROVED | 관리자 `승인하기` | SC-A-04 오늘의 프로그램 | 전부 | 되돌리기 → PENDING |
| REJECTED | 관리자 `받지 않음` + 사유 | SC-A-03 — **사유 그대로 노출** | 게임 · 걷기만 | 되돌리기 → PENDING · 재신청 미정 `FV-05` |

**불변식 5가지** — 이것만 깨지지 않으면 됩니다.

1. 번호가 바뀌면 무조건 CHECKING 이전으로 돌아간다. 인증·자동채움은 남지 않는다.
2. NEEDS_OTP 계열에서는 이름·동 필드에 **어떤 값도 채워 넣지 않는다.**
3. SUBMITTING 중에는 어떤 입력도 받지 않고, 실패 시 **입력값을 하나도 잃지 않는다.**
4. PENDING에서도 **앱 설치와 로그인은 막지 않는다.** 교실 기능만 잠근다.
5. PENDING → APPROVED 전환으로 **화면이 저절로 바뀌지 않는다.** 사용자가 버튼을 눌러야 넘어간다.
