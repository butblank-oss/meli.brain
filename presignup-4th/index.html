1. 목적과 범위

3기 종료 리포트는 볼 만한 사람은 이미 거의 다 봤습니다(11/9 기준 열람 243명, 3기 932명 중 26%). 같은 홈 배너 자리를 4기 미리 신청 배너로 바꿔 재등록을 늘립니다. 재등록 목표는 280명이고, 11/9 기준 사전등록은 137명입니다.

  • 이번 범위: 홈 배너 1개, 4기 신청 화면(교실과 신청자 정보 확인)과 약관 시트, 신청 완료, 신청 내용, 미등록자 안내, 마감 안내, 전화 문의
  • 설계 원칙: 한 화면에 한 가지 일만 둡니다. 모든 화면이 375 × 812에서 스크롤 없이 들어가고, 주요 버튼은 하단에 고정합니다.
  • 범위 밖: 홈 전체를 쉬는 기간 모드로 바꾸는 작업, 멈춘 순위, 활동 잠금, D-day 표기 (이전 핸드오프의 쉬는 기간 화면들)

2. 사용자 상태

배너를 누를 때마다 서버에 신청 상태를 조회하고, 결과에 따라 이동할 화면을 정합니다. 배너 모양은 상태와 상관없이 같습니다. 상태는 저장값이 아니라 조회 때 계산하는 값입니다(데이터베이스 탭 참고).

3. 배너 노출

  • 노출 대상: 로그인한 모든 사용자. 신청 상태에 따라 숨기거나 문구를 바꾸지 않습니다.
  • 노출 위치: 홈 상단, 기존 3기 리포트 배너 자리. 3기 리포트 배너는 같은 배포에서 내립니다.
  • 노출 기간: 배포일부터 신청 마감일까지 마감일 확인 필요. 마감 후에는 서버 설정으로 내리고, 앱 업데이트 없이 끌 수 있어야 합니다.
  • 문구는 날짜만 쓰고 D-day는 넣지 않습니다. 서브 문구 “내년 2월 1일 시작 예정이에요”(B-01), 달력 아이콘은 날짜 글자 없이 모양만 (통합본 변경, v4는 “2027년 / 2월 / 1일”).
  • “내년”은 2026년 안에서만 맞는 말이라, 2027년 1월 1일 이후에도 배너가 남아 있으면 서브 문구를 “2월 1일 시작 예정이에요”(B-01b)로 바꿉니다. 서버에서 바꿀 수 있어야 합니다.
  • 360px 미만 기기는 짧은 문구(B-01s)를 쓴다고 QA-03에 적혀 있지만, 정의서에 B-01s 문구가 없고 프로토타입은 같은 문장을 씁니다 확인 필요

4. 신청

  • 3기 등록 정보(이름, 연락처, 사는 동)를 그대로 써서 신청합니다. 앱에서 따로 입력받지 않습니다.
  • 정보가 바뀐 사용자는 앱에서 고칠 수 없고, 치매안심센터 전화로 안내합니다(S6).
  • 순서: 신청 화면(교실과 신청자 정보 확인) → 약관 시트. 약관 시트의 [동의하고 신청하기]가 실제 신청 요청입니다.
  • 필수 동의 2개(개인정보 수집·이용, 제3자 제공)에 모두 체크해야 버튼이 켜집니다. “모두 동의해요” 한 번으로 둘 다 체크됩니다. 기수마다 동의를 새로 받습니다.
  • 동의하지 않으면 신청할 수 없습니다. 버튼 아래에 “필수 항목에 모두 동의해야 신청할 수 있어요”를 보여줍니다.
  • 한 계정은 4기에 한 번만 신청할 수 있습니다. 중복 요청은 서버가 막고 S3로 보냅니다.
  • 신청 취소는 앱에서 받지 않고 치매안심센터 전화로 처리합니다.
  • 거주지(남동구)는 앱에서 막지 않고 보건소가 사후 확인합니다 확인 필요

5. 알림

  • 개강 전날 신청자 전원에게 문자를 보냅니다. 화면에는 “개강 전날 문자로 알려 드려요”로 안내합니다. 개강 전날인 2027년 1월 31일은 일요일입니다 발송일 확인 필요
  • 신청 직후 완료 문자를 보낼지 정해야 합니다 확인 필요
  • 4기 신청은 실제 문자가 나갑니다. 테스트는 반드시 본인 번호 계정으로만 합니다.

상태 조회 · 신청 처리 순서

GET apply-status 계산 순서 제안

  1. cohort.banner_enabled = false면 배너를 그리지 않음 (조회 대상 아님)
  2. 내 user_id 또는 3기에 등록한 연락처의 phone_hash로 status='APPLIED' 신청이 있으면 → APPLIED (마감보다 먼저 봄, O-17). 연락처로 찾은 웹 신청서 신청은 이때 user_id를 채워 연결 O-10
  3. 지금이 apply_close_at 이후이거나, capacity가 있고 APPLIED 수가 정원 이상이면 → CLOSED
  4. 직전 기수 cohort_member에 이름과 연락처가 모두 있으면 → ELIGIBLE (profile은 가려서 내려줌)
  5. 그 외 → NO_PRIOR (form_url)

POST apply 트랜잭션 제안

  1. 같은 Idempotency-Key로 이미 처리했으면 그때 결과를 그대로 돌려줌
  2. 마감 조건이면 410, 저장 없음
  3. 살아 있는 신청이 있으면 409, 저장 없음
  4. cohort_application 1행 + consent_record 2행 + sms_dispatch(PRE_START_REMINDER) 1행을 한 트랜잭션으로 저장. 하나라도 실패하면 전부 되돌리고 5xx → S1-4 (A-09 “실패 시 저장 없음”)
  5. 동시에 두 요청이 들어와 고유 인덱스에 걸리면 409로 바꿔 응답
  6. 정원이 있으면 마지막 자리 경쟁을 막기 위해 cohort 행을 잠그고 수를 셈

웹 신청서와의 통합

3기 미등록자는 S4를 거쳐 meli.health/invitations/dementia에서 신청합니다. 11/9 기준 사전등록 137명 중 23명은 보건소 신청폼(보건소 직접 접수)으로 들어왔습니다(report-3rd-hc 보고 페이지 기준). 이 경로가 웹 신청서와 같은 것인지는 O-06에서 확인합니다. 앱과 웹 신청이 한곳에 모여야 중복 1건 규칙과 APPLIED 판정이 맞습니다.

방식내용좋은 점걸리는 점
A. 한 표 추천 제안웹 신청서도 cohort_application에 platform=web, entry_point=web_form, user_id=NULL로 저장. 앱 상태 조회 때 연락처 해시로 찾아 user_id를 채움중복 판정과 집계가 한 번에. 보건소 명단 추출이 쉬움웹 신청서 쪽 저장 코드를 바꿔야 함. 같은 번호를 가족이 같이 쓰는 경우 잘못 연결될 수 있음
B. 따로 두고 합쳐 읽기웹 신청서 기존 표는 그대로 두고, 두 표를 합친 뷰로 상태를 판정웹 신청서을 건드리지 않음중복을 고유 인덱스로 막을 수 없어 409 판정이 느슨함. 동의 기록 구조가 둘로 갈림
어느 방식으로 할지, 연락처로 계정을 연결해도 되는지는 개발팀과 보건소가 정할 일이라 확인 필요 O-06 · O-10에 올려 두었습니다. 3기 리포트 S7-11은 “참여 의사만 저장”으로 적혀 있어, 이것을 4기 신청 1건으로 볼지도 같이 정해야 합니다.
